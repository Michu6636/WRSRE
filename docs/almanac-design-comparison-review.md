# Independent review: Almanac design comparison `d0b3f05`

The agent's [comparison](almanac-design-comparison.md) is preserved byte-for-byte from commit `d0b3f05b8d7be7f13a93e821a84da97813baf4ca`. It is a static design lead, not an approved implementation or test. In particular the author's claimed `git ls-remote` and execution status are agent reports; the review here compares repository files and disassembly, not a Windows runtime.

## Independent source checks

- **Property tax:** [`SettlePropertyAll`](../plugins/taxes/taxes.cpp) starts with `g_propertyTaxFlat` and, if `g_propertyLandValue` is enabled, multiplies it by `0.50 + 1.50 * TsmAttractiveness(b)`. The shipped [`taxes.ini`](../plugins/taxes/taxes.ini) sets `property_land_value = 1`. Thus the field is a per-enterprise **base** when scaling is enabled and the actual charge can vary; it is flat when scaling is disabled. The [plan](almanac-plan.md) and [technical findings](almanac-technical-findings.md) now say this, without changing the simulation or deciding whether to change its rules. The tax API header and old plugin summary also call the amount flat; don't assume their wording specifies the full settlement formula. The actual active configuration and resulting in-game charge still require validation. An authoritative policy snapshot should expose the active basis or the UI should mark it unavailable, not infer the current setting solely from the shipped INI.
- **Units:** [`taxes_api.h`](../src/taxes_api.h) explicitly specifies the property setter value in active-currency units. `SetTaxRateImpl` directly assigns it to `g_propertyTaxFlat`; `SettlePropertyAll` uses that value and the currency service's `moveTreasury`. Separate startup code converts the RUB-denominated INI base to USD or accepts the USD override. This supports the stated contract and no additional conversion **in the setter**; it does not establish behavior through all save/load or currency-switch scenarios. Avoid saying the property unit is wholly unknown.
- **Configured values:** effective VAT/profit getters return zero when disabled; no generic property-value getter exists. `SnapshotTaxes` already copies all configured rates and enable flags under the plugin's lock for its own City Hall view, but it is private and not a service. A versioned, authoritative policy snapshot/getter is a sound candidate; the service registry matches exact versions, so preserve all required old views, sizes and consumers. The API design must include validity, basis, units and disabled values, and account for concurrency and persistence. No implementation is authorized.
- **Nonfinite input:** `SetTaxRateImpl` rejects NaN; VAT/profit range checks reject positive infinity, but the property check is only `rate >= 0.0f`, so positive infinity passes that check in the source. Do not assume every nonfinite value is rejected. This is a static finding, not a demonstrated runtime incident. Before implementing controls, specify finite-value validation and tests at the authoritative boundary; do not silently patch the game or tax plugin in this planning step.
- **Financial flows:** `state_ledger` currently consumes currency flow events, aggregates private in-memory monthly values, calculates observed treasury change and unexplained divergence, and can write CSV when enabled and a persistence/save directory is available. It publishes no query service. The currency observer is in the v3-compatible prefix and can be consumed through appropriate version/size handling; its events cover labelled currency operations, not necessarily every treasury change. A versioned ledger snapshot is a candidate, but it must label period, active currency, completeness, startup/reload/rewind state and flow-vs-treasury divergence. A separate observer is not automatically full history. A private ledger can be a useful data source once it publishes a contract; the report's 'not usable as the authority' should not be read as a verdict that its observed flow data are inherently invalid.
- **UI authority:** City Hall's controls already call the same underlying tax service setter implementations and take a locked internal snapshot. Two control surfaces can safely share one authority in principle; separate controls are not themselves duplicate tax logic. Their consistency, behavior during editing and after save/load still need tests. Unavailable services must be labelled **unavailable**, not asserted to be definitely 'no tax' merely because the panel could not resolve a provider.

## UI evidence and operational caveats

- The normal loop remaps the third **visual position** to the final vector entry, with conditional skips. It is not a rule that every vector 'index 2' is the final record. The alternate loop skips the last entry only on the analyzed path; do not infer actual live mode coverage or claim every native icon remains clickable until tested.
- S5 in the source document still says 'to show the mod hit-test can run first', conflicting with the qualified summary. The objective is to establish safe ownership and routing; handling before native is not a predetermined requirement. Similarly a native index change is not sufficient for repeated clicks, changing sidebar sections, or Esc.
- The native insertion helper [`FUN_1404492f0`](../export/almanac-evidence/FUN_1404492f0_disasm.asm) includes a capacity comparison and a conditional growth call. No separate DLL-side check does not prove overflow or safe mutation. Fit, valid ownership, reallocation and texture lifetime remain open.
- A restart with a future switch off is a **candidate**, not an established rollback. No Almanac switch, procedure or test exists. The no-runtime-removal statement describes the examined Reputation insertion, not a constraint on a future independent Almanac design.

## Follow-up on the unshared implementation-spec summary

The proposed `docs/almanac-implementation-spec.md` was reported as uncommitted in another workspace and is not available here; only the user's pasted summary was assessed. The existing ledger's `OnFlow` ignores its currency argument, so mixed-currency inputs could be summed without distinction; no mixed-currency event stream was observed. The existing accumulator does not record completeness or currency provenance, so a new snapshot cannot reliably flag them without additional tracking from an appropriate baseline; unknown must remain unknown. `OnSaveLoad` also resets the accumulator and first-tick baseline on loads, not only on backward time jumps.

`LoadTaxes` checks the current fixed header's minimum length, magic and version and returns without loading when these fail. An incompatible new layout/version could make legacy tax policy fail to load; it does not follow that every layout change discards the entire game save. The saved property base can later replace the startup-converted value, while the setter can replace it directly, so its origin is not always just the startup configuration. Save/load, currency units and migrations need explicit compatibility tests.

If an append-only tax v3 interface is eventually designed, a bounded v2 `structSize` and preserved exact-version v1/v2 behavior are sound compatibility goals; a copied v2 view is one approach, not the only possible layout. Do not assume old compiled consumers automatically use a newly appended function merely because a size is larger. The input validation proposal must distinguish an Almanac-side guard from the independent existing service accepting positive infinity: UI-side validation alone does not protect other service consumers. Changes to any setter require their own approval; preserving existing tax rules does not require preserving acceptance of nonfinite inputs, but the trade-off must be evaluated.

`ui_panels` is building/person-oriented and does not establish a global sidebar host. `ui_overlay` does provide an existing global HUD draw callback, but its column/visibility semantics do not establish a safe interactive Almanac panel. Both are precedents, not a completed global-panel integration. A data-only proof of concept or geometry probe may still require code, plugin loading or process modifications and is not implicitly read-only or authorized.

## Decision gate

Path B (a dynamic same-row independent button) remains the initial lead; Path A (native insertion) remains a viable alternative to evaluate. The separate global panel is preferred and the Economy & Trade page is an accepted fallback with the required same-row button. First release still needs meaningful finance data and directly adjustable tax policy. The next work should be a focused integration and service-contract design with failure states and an eventual tightly scoped test proposal, not another broad scan. A live test, hook or implementation requires separate explicit approval and a verified backup/restore plan.
