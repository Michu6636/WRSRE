# Live snapshot: address-indirection correction

**Scope:** Review of the Windows agent's [read-only snapshot and raw values](../export/almanac-evidence/live-snapshot-20261109/) from upstream `913c277c74e1f0f23ddb1694cb292a8fd19c5af0`, preserved unchanged. This workspace cannot access the Windows process and has not independently verified the reported live data or file hash.

The report records the expected executable hash and an ASLR module base, but all subsequent game-relative reads failed. The failure does **not** establish that the game object address is wrong: the attempted reads used a misinterpreted address.

- Prior caller evidence and the earlier [snapshot](../export/almanac-evidence/geometry-snapshot-20261108.md) identify `module_base + 0x9d4f10` itself as the inferred inline game-object address on a particular host call path. This is a static inference, not proof of runtime reachability. The report instead treated the first eight bytes at that address as a pointer and tried to read fields relative to the resulting value. Therefore its error-299 failures do not test `module_base + 0x9d4f10 + field_offset` and do not establish that those fields are inaccessible.
- The host's repeated `LEA` instructions likewise use `module_base + 0x9be060` as the address of a shared panel object. The eight bytes read at that address must not automatically be called its address or a pointer to it. The meaning and runtime identity of the object and those bytes remain unverified.
- The report repeats the unsupported `0x60` trade-entry stride. The row instructions support `0x50`; see [trade-trace review](almanac-trade-trace-review.md). The failed snapshot supplied no vector data and cannot settle the row count, capacity, selection or handler state.

## Corrected retry

The agent's [retry report and raw identity file](../export/almanac-evidence/live-snapshot-retry-20261109/) from upstream `b1b5d94` are preserved unchanged. The report says the corrected direct-address reads succeeded, with selector byte 1, selected index 0 and eight `0x50`-byte entries. Its listed begin/end/capacity values are arithmetically consistent with eight occupied slots and space for one more: `end - begin = 0x280`, `capacity - begin = 0x2d0`. A momentary spare slot does **not** establish safe mutation, pointer lifetime, visible placement, or a ninth click.

The hex dump in the report for `game+0xc650` decodes to its stated pointer, and the four floats at `game+0xae50` decode to `184`, `785`, `916.7998`, `0`. The physical meaning of these floats and of the two equal qwords at `game+0xadb0` is not established by this snapshot. The separate `raw-values.txt` contains identity and address only; vector header and individual-entry raw bytes are not preserved, so the agent's decoded text IDs and drawable pointers cannot be independently re-decoded from the shared evidence. The selected panel's name was not included, so this report does not independently prove the pointer refers to `trade`. The snapshot is non-atomic and neither selector value nor matching build proves execution of a particular handler.

The accompanying user summary says `-1 >= 8` is false. That is not the instruction's comparison. At `0x140373fcc`, the 32-bit load into `EAX` zero-extends `0xffffffff` to `0x00000000ffffffff` in `RAX`; `CMP RAX,RDX`/`JNC` performs an unsigned comparison. `RDX` comes from the separate `game+0x10bd0/+0x10bd8` span, not the eight-entry trade vector. It is not measured in this report, so do not infer actual control flow from `-1` versus the trade count. See [trade-trace review](almanac-trade-trace-review.md).

## Paired normal-selection snapshots

The Windows agent's [two snapshots](../export/almanac-evidence/live-snapshot-selection-change-20261109/) from upstream `6e436f2` are preserved unchanged. An [independent decode](../export/almanac-evidence/selection-change-independent/decode.txt) confirms that both sets include eight 80-byte raw entries, with byte-identical entries across captures. Their `+0x40` DWORDs and `+0x48` pointers match the reported values. The first two record names before NUL are `importexport` and `productionconsumption`; these are **sub-entry names**, not proof of the parent panel's name or a separate sidebar dispatch.

The raw selected-index bytes decode to 0 and 1; `game+0xae58` bytes decode to approximately 916.8 and 732.4. The reported selector, selected-entry pointer, vector header values and separately reported `game+0x10bd0/+0x10bd8` values match across the captures. The latter span is `0x50` bytes, which the host's separate 40-byte-stride count arithmetic would yield as two, **if** the reads were consistent; it is not the eight-entry trade vector. `game+0x10be8` was not included in these two samples. Raw parent-record bytes/name and raw vector-header bytes were not provided; do not claim they were independently verified.

Only two **reported sampled fields** differ; the captures are non-atomic and more than 23 minutes apart, so they do not prove that nothing else changed, or that the manual selection alone caused every difference. Their values do not establish handler execution, a ninth button's fit, clipping, or custom content replacement/cleanup.

## Sidebar switch and return

The [three original snapshots](../export/almanac-evidence/sidebar-return-20261109/) from upstream `ef07903` are preserved unchanged, alongside an [independent raw decode](../export/almanac-evidence/sidebar-return-independent/decode.txt). The user described the middle state as another sidebar section; its actual name and parent record were not captured in the report. The selected pointer changed and then returned to its previous value. Selection bytes decode to `1`, `0xffffffff`, `0`; eight 80-byte entry records are byte-identical between states 1 and 3. The middle state's reported vector header values are all zero, but its header's raw bytes were not included. This does not demonstrate the trade vector was destroyed and rebuilt, nor does it prove that all state was restored or the middle value means no selection in every context.

The `game+0xae58` floats were approximately `732.4`, `904`, `916.8`. The 16 bytes at `game+0xadb0` match within this sequence, but differ from the preceding selection-change sequence; their meaning is not established and they cannot be assumed to be fixed geometry. The selector is unchanged, and these non-atomic observations don't establish an executed function or the custom Almanac's close/return behavior. The native switch **observed here** resets the previously selected index to zero on return, useful as one possible design precedent rather than a universal rule.
