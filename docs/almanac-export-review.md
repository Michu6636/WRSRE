# Almanac: independent review of the two trade-handler exports

**Scope:** static review only. No game run, debugger, database query, hook, or implementation. The exports were fetched from commit `14c9a07fba1f09f2d8f61fef70bb08100173c77b` of the existing investigation. They are Ghidra disassembly output, not the executable; its hash and the runtime path have not been independently verified here. Addresses below are preferred-image VAs (image base `0x140000000`), not runtime addresses.

Sources: [`FUN_140373EA0` disassembly](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm) and [`FUN_140361BB0` disassembly](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/ch_tab23_full.asm). The older `docs/almanac-investigation.md` in that commit contains conflicting claims; the review below is scoped to the cited instructions and does not validate that entire report.

## 1. Both row loops can conditionally skip entries

The earlier claim that `FUN_140373EA0` draws every sub-entry without skips is **incorrect**. In its row loop, the mapped sub-entry index is in `EBX`:

```asm
1403741cf  CMP dword ptr [RSI + 0x578],0
1403741d6  JZ  0x1403741e4
1403741d8  LEA EAX,[RBX - 3]
1403741db  CMP EAX,1
1403741de  JBE 0x1403743b6
1403741e4  CMP EBX,6
1403741e7  JNZ 0x1403741f6
1403741e9  CMP dword ptr [RSI + 0x5e0],0
1403741f0  JZ  0x1403743b6
```

A nonzero `game+0x578` skips mapped indices 3 and 4; index 6 is also skipped if `game+0x5e0` is zero. Both jumps land at the iteration increment, past the X advance at `0x1403743a8`, so skipped entries do not consume a horizontal slot. See [the mapping and skip checks](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L159-L183) and [the draw/advance/loop tail](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L260-L282).

For the conditional example of **four sub-entries**, the mapped order is `[0, 1, 3, 2]`. If `game+0x578 != 0`, index 3 is skipped, giving drawn order `[0, 1, 2]`. If the relevant skip conditions are absent, all four are drawn. This does not establish the actual runtime count or flag values.

`FUN_140361BB0` also has conditional skip checks, applied to its linear iteration index; its loop bound is the calculated sub-entry count minus one. Its X advance is likewise bypassed on a skip. See [its count and skip checks](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/ch_tab23_full.asm#L183-L208) and [its advance and loop tail](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/ch_tab23_full.asm#L310-L333). For a stable four-entry collection with no skips, this loop attempts three entries, not the four claimed in the older report's §42. But a stable five-entry collection with `game+0x578 == 0` attempts four: seeing four buttons does not prove which handler is active. Both examples assume the normal row path; neither establishes actual runtime state or visible output. Thus neither handler supports a fixed button position without considering its active flags, count, scale and row state.

Additionally, both handlers test `game+0xc7d4` and branch away from their regular vector-row loops when it is not `-1`: [373EA0](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L130-L143), [361BB0](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/ch_tab23_full.asm#L165-L181). The meaning and runtime frequency of that condition remain unknown.

The host's specific trade-branch call to `361BB0` zeros `R9D` immediately before the call ([host](https://github.com/Michu6636/WRSRE/blob/b6b49c8ba1b5b770c076864f76134aa99cd6e4bd/export/140317db0_full_disasm.asm#L5767-L5768)); the handler saves `R9` in `R15`, and does not replace it before the test at `0x140361f09` ([entry](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/ch_tab23_full.asm#L27-L29), [test](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/ch_tab23_full.asm#L165-L166)). Therefore that test's nonzero branch is not taken at this call site if reached; it may apply to other callers. An earlier `0x140361ca7` path can still exit before the test, and `game+0xc7d4` can still divert the row. This is static call-site reasoning, not runtime reachability proof.

## 2. A change to `game+0x10be8` is not a click event

On the path into the normal row in `FUN_140373EA0`, the handler writes `-1` to `game+0x10be8` at `0x14037403a` **before the row loop**, independent of a row click. A different early path calls another function and branches away. See [the initial comparison and reset](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L60-L82). `FUN_140361BB0` also resets the field before its normal row at `0x140361cbb`: [initial path](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/ch_tab23_full.asm#L46-L54).

Consequences for a proposed before/after comparison: a change to `-1` can happen without a row click, and a click can write `-1` when it is already `-1`. This is a concrete false-positive and false-negative risk; the transition must not be used as the row-click signal.

## 3. Click paths differ between the two handlers

In `FUN_140373EA0`, the button collision result is tested at `0x1403742a4`–`0x1403742ac`. On a hit, a UTF-16 string-copy loop at `0x1403742d0`–`0x1403742e2` exits when `CX` is zero; there is no intervening change to `CL` before `CMP [0x140a54e91], CL` at `0x1403742f2`. Thus, on this path, the comparison is against zero. The selected-index write and `-1` write at `0x140374356` and `0x14037435c` are reached even if that index was already selected; the `game+0x1039a` write at `0x14037434f` is conditional on a change. Sound is conditional, not a dependable unique click signal. See [the complete bounded sequence](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L216-L255).

In `FUN_140361BB0`, after a successful collision check, an indirect call through `0x14086c8b8` at `0x14036213b` returns a value tested at `0x140362141`; zero branches around the selection and `-1` writes. See [the collision, gate and writes](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/ch_tab23_full.asm#L247-L298).

The user provided subsequent Ghidra excerpts reporting `PTR_GetMouseLeftPress_14086c8b8`, an imported external `C3DDLL64.DLL::C3D_INPUT::GetMouseLeftPress`, and slot bytes `A0 A5 98 00 00 00 00 00` (little-endian `0x98a5a0`). The reported data at preferred VA `0x14098a5a0` is in `.rdata` and starts `F3 04 3F 47 65 74 4D 6F 75 73 65 4C 65 66 74 50`, consistent with a PE hint and name beginning `?GetMouseLeftP`, not executable code. The report identifies this as an unbound import; the pasted excerpt does not itself show the import descriptor tying this slot to the DLL or the full name. The original query files, executable and project are not independently available here. Neither the name nor these bytes establish edge/held behavior or consumption, and the raw slot value is not a verified runtime pointer. **Correction:** an earlier review called this an import based on the call form alone; that inference was not established.

The row's gate differs from `373EA0`'s direct byte check, but this is not a function-wide distinction: its export also calls the same slot later at [`0x1403754cb`](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L1193-L1198). The direct byte `0x140a54e91` is numerically `0x301` bytes after the `0x140a54b90` address passed in RCX to the indirect call. This is a useful candidate relationship, not proof of an object member, shared state, equivalent behavior, consumption or execution of both paths in one frame.

A future design needs an actual click signal **plus** the correct hit test, active-handler behavior, window/input gates and same-frame ordering. Cursor position alone proves only hover.

## 4. The proposed body interception remains unproven

At `0x1403745b6` the first two instructions occupy 9 and 8 bytes and use RIP-relative addresses. `InstallInlineHook` in `src/tesmioloader.cpp` supports a 17-byte stolen region, but copies those bytes to a trampoline without relocating their operands. Therefore that existing helper cannot blindly trampoline those instructions. The export shows both the `JLE` at `0x14037419c` and the `JMP` at `0x1403743ed` targeting the **start** of the site; the alternate path also falls through after `0x1403745b0`. Entry at the start is not inherently a jump into the middle of a patch, but every incoming route and any interior targets must be assessed. See [the loop exits](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L155-L158), [the regular-row exit](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L280-L285), and [the site](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L362-L380).

A different relocation mechanism might be possible, but safe live-register preservation, stack/cleanup and output handling, skipped state effects, and the alternate handler are unverified. The [373EA0 tail](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L12414-L12448) calls helpers with four stack-local addresses before restoring registers and returning. In the [normal path](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L84-L94), `[RBP+0x50]` is initialized before the row; `[RBP-0x70]`, `[RBP+0x510]` and `[RBP+0x90]` are initialized after the proposed interception point at [`0x14037464c–0x140374680`](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L397-L408), [`0x140374752–0x14037475b`](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L445-L447) and [`0x1403749eb–0x1403749f2`](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L613-L614) respectively. A [normal exit path](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L721-L732) writes through both output pointers before entering the cleanup. The [trade caller](https://github.com/Michu6636/WRSRE/blob/b6b49c8ba1b5b770c076864f76134aa99cd6e4bd/export/140317db0_full_disasm.asm#L5757-L5765) initializes both outputs to zero and computes `game+0xae58` from the R8 output after this handler returns.

**Correction to a subsequent user-supplied report:** the early path at [`0x140374027–0x140374035`](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/140373ea0_1403829fd_disasm.asm#L74-L82) does write both outputs, but jumps to `0x1403826f7`, **past all four** cleanup calls, not into them. It then performs the stack-cookie check and register-restoring epilogue. Because this early path exits before the normal path's first local initialization, it does not prove that skipping the same cleanup from after the row is safe. Conversely, jumping from the post-row interception directly to the full cleanup would pass later, uninitialized locals to those helpers. The alternative `361BB0` also has [separate exit destinations](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/ch_tab23_full.asm#L14748-L14752): `0x140373e25` calls a helper on `[RBP+0x110]`, while the [early branch](https://github.com/Michu6636/WRSRE/blob/14c9a07fba1f09f2d8f61fef70bb08100173c77b/export/ch_tab23_full.asm#L46-L53) jumps past it to `0x140373e31`. This does not establish a safe suppression point in that handler either. Live state, all skipped effects and both output values still require investigation; no hook is approved or specified here.

## 5. Independent review of the host export

### Proposed runtime-observation plan: corrections

A user-supplied read-only diagnostic plan proposes observing trade dispatch and row execution. It has not been run or approved. Before using it:

- The repository records v1.1.1.9, PE timestamp `0x6a3eb6ad`, and an earlier investigation reports SHA-256 `296644a9f207d609031fc2ae73fed2dcb34619a1d55a35d1c7b51965ce6841b8` and 10,308,608-byte file size. The PE timestamp/version alone do not prove identical binaries; the previously reported hash and its linkage to the current exports have not been independently verified. Compare the running executable's hash with the actual Ghidra-imported executable's hash if available and confirm relevant instruction bytes; otherwise report the identity limitation. Runtime addresses require the loaded module base plus the RVA, including the scale at **`B+0x992088`**, not the preferred VA when ASLR relocates the image.
- `361BB0` does **not** draw at most three buttons: with a stable five-entry collection and no applicable skips, its `count-1` loop attempts four. A four-entry collection produces three normal-loop iterations before skips. Do not label either handler as the observed mode until the relevant host dispatch and selected entry are observed.
- The specific fifth-coordinate estimate `[386,450)*scale` is conditional, not a runtime measurement. A screenshot without the fifth button cannot prove that a hypothetical button will draw correctly or be clickable; it can only show current visible space and support a tentative layout estimate. Clipping, hit-testing and overlap remain unresolved.
- A staged plan can begin with only the two host call instructions `B+0x31edef` and `B+0x31ee13`. For normal row execution, `B+0x374217` in `373EA0` or `B+0x362010` in `361BB0` are candidate second-stage points after skip checks, subject to verifying live bytes and control flow. At those row sites the saved game pointer is in `RSI` for `373EA0` and `R14` for `361BB0`; do not carry the host's `R14` convention into the first handler. A missed row breakpoint can also mean an early/alternate path, not necessarily a wrong build. `0x14036220e` is the loop increment, `0x140362245` is the loop-back conditional, and `0x14036225d` is a post-loop setup address, not a proven universal content boundary.
- An observational debugging session still affects the running process: breakpoints pause execution, and software breakpoints temporarily modify instruction bytes. Whether non-patching hardware breakpoints are available is tool-dependent. No data writes, save edits, tax changes or permanent patches are part of the plan; approval, debugger availability, game state and safe stop/detach procedure must be established first.

## 6. First-release finance data: independent source review

- [`currency`](../src/currency_api.h) exposes a treasury balance and active-currency helpers; these are a practical source for current balances, subject to service availability and version guards.
- [`state_ledger`](../plugins/state_ledger/state_ledger.cpp) consumes currency flow observations and keeps its current flows and most-recently-closed HUD values in private state; it does **not** publish a service. A separate Almanac plugin therefore cannot simply request that snapshot. At month end it separately computes the observed treasury change and `flowDelta` from reported flows; `g_hudClosedNet` is the latter, while the difference is calculated as `unexplained` and passed to CSV. Labeling the flow sum as the whole observed treasury change would mislead players. CSV output can be disabled or unavailable, and load resets the in-memory closed-month marker.
- For planning, consider adding a versioned, lock-protected ledger snapshot exposed by the ledger owner, carrying period/currency, observed change, reported flows and unexplained difference, plus validity/availability status; exact synchronization and save/load behavior require design. Do not duplicate the ledger as a second authority or silently use zeros when data is missing. This is a proposed future API, not an implemented feature.
- [`taxes_api.h`](../src/taxes_api.h) provides setters and enabled flags, but VAT/profit rate getters return effective zero when disabled, and property tax has no public configured-value getter. A future policy snapshot/getter should preserve configured values when suspended and expose property as a flat amount, while preserving existing accrual-getter behavior and exact-version registry compatibility. These are planning requirements; no API changes are authorized or implemented.

## Decision and next evidence

**Not ready for implementation.** The active runtime handler and state, visible bounds/clipping, native content suppression, return-to-vanilla interaction and close handoff remain unverified. The disassembly does not establish that a new same-row button fits, nor that the proposed suppression preserves vanilla behavior.

A later user-supplied static review reports constants 45, 85 and 64, and proposes a fifth rectangle from `386 * scale` to `450 * scale` when four 64-unit buttons are drawn without gaps.
