# Independent review of two Reputation UI investigations

Both reports were initially provided as pasted text. Agent 2 subsequently published commit `46679f21146b2ee90c59cddf0f2a37c0c08b152a`. Its [row-item analysis](almanac-row-item-vs-button-analysis.md), [mechanism report](reputation-sidebar-ui-mechanism.md), and both evidence folders were copied byte-for-byte without overwriting anything; all 51 Git blobs matched the source. All five checks in its [input manifest](../export/almanac-row-item-analysis-20261110/INPUTS_sha256.txt) match this checkout. The DLL is the previously reviewed `fd7d94590b98c7eb80fa14ef95f2bbdf4b5e058f68d07dfa97d0db8dcbfbcb6a`; the preserved native listings are not an authenticated copy of the user's installed executable. Agent 2's newer alternate-content-close comparison remains uncommitted on its own workspace and was not available here; only its pasted summary could be reviewed.

## Verdict

The second investigation is the stronger lead: it identifies both native row loops, traces item insertion and selection, and distinguishes the main sidebar entry from the optional trade item. Still, its paste contains unverified or overbroad conclusions. The first report repeats several serious false function identities independently corrected in [the Reputation review](almanac-reputation-review.md); it must not guide implementation as written.

## Independently checked findings

- [`FUN_1404492f0`](../export/almanac-evidence/FUN_1404492f0_disasm.asm) copies an 80-byte entry and invokes `0x14044c410` when end equals capacity. That is a native growth path, not proof that arbitrary plugin insertion, growth, allocations or rollback are safe. Agent 1's `(end-begin)/0x50` is the **count**, not capacity; capacity is `(capacity-begin)/0x50`. A previous snapshot already observed eight entries and room for nine at that instant, not guaranteed future fit or safety.
- [`FUN_140361BB0`](../export/ch_tab23_full.asm) enters its row loop only for count greater than one and its back edge at `0x140362241–245` checks `index < count-1`. In that loop, an appended last entry is omitted. Additional conditional skips occur; its actual invocation under a user's mode has not been observed. This supports agent 2's warning for that path, not proof that every path hides the item. The alternative standalone button has **not** been shown to work in that mode and cannot be described as unaffected.
- The previously reviewed normal loop maps index order `[0,1,7,2,3,4,5,6]` for eight entries and `[0,1,8,2,3,4,5,6,7]` for nine, assuming no additional skips. Native index 7 moves from third to ninth; appending need not preserve order, but this alone is not a violation. Native handling and remapping can both be true; the remap does not by itself refute the config's 'generically' claim.
- [DLL selection excerpts](../export/almanac-evidence/reputation-comparison-independent/) show `0x180057617` storing the first passing case into a plugin global, while `0x180057623–678` calls the row-selection predicate and, only on a change to true and when the guarded flags are clear, dispatches a **previously stored** value at `0x180411bcc`. This supports agent 2's caution that the argument is not freshly computed from the item index on that path. It is not a proof of a particular first-click effect without proving runtime initial state and all writers. It observes a selection transition, not necessarily a repeated click. The printed opening message is not proof of a visible window. The dispatcher's common tail also contains conditional logic; its complete UI behavior remains unresolved.
- The same DLL [panel-detour excerpt](../export/almanac-evidence/reputation-comparison-independent/panel-detours.asm) has return-address comparisons against executable base `+0x31e478`, `+0x31e4b2` and `+0x31e509`, and a conditional path from the first to the sizer. Those are compared **return addresses**, not demonstrated hook installation targets. DLL stores to `g_ui+0xae54/+0xae58` are independently recorded in [the geometry review](almanac-reputation-review.md#independent-follow-up-panel-geometry-writes). The full capture/render/restore behavior is still not independently established.

## Specific corrections

- Agent 1 calls `0x180068a20/a80/ae0/b40` item callbacks and `0x180068ba0` a panel-close routine. Import names and registration show file-open wrappers and `UnhookWindowsHookEx`, respectively. `0x1800303e0` is a file-path/mode helper, not demonstrated as an item-click handler. It also presents logging constants as hook registrations and wrongly dismisses an alternate native handler. Its comparison table and proposed validation are therefore unreliable.
- Agent 1 treats the main left-column button as fallback satisfying the requirement. It does not replace the required same-row button. The existing independent-button candidate is a separate *dynamically placed same-row* button, not this left-column item. A wider product trade-off needs the user's decision.
- Agent 2's suggestion that a standalone button is unaffected by the alternate handler, or that the DLL body **only** draws when the left-sidebar entry is selected, goes beyond this bounded review. Its first-click claim depends on prior global state; its screenshot inference is not independently corroborated. The effective settings matter: the supplied config says `in_panel` forces `sidebar_hides_panel` off, even though the latter's literal value is 1.
- `sidebar_item = 1` is a live mod test, **not** a read-only observation. Disabling it and restarting is not, by itself, verified rollback for every changed file, loader, hook, process state or save. A selector snapshot does not prove which handler executed. A complete authorized test must observe all eight native icons and the new one, repeats, close/return, and relevant modes, not only three icons. No implementation or live test is authorized by this review.

## Follow-up on commit `46679f2` and the newer pasted summary

- In the alternate handler's bounded row loop, an eight-entry vector would enumerate indices 0–6 before skips; with an append, it would enumerate 0–7 before skips. This applies **if that loop is actually reached** and sees the same vector. It does not show that the user's eight-icon runtime view already lacks an icon; another path, mode, record, or draw could differ. Neither the selector value alone nor these static listings prove active execution. Nor does it make the normal handler the only possible way to satisfy the requirement.
- Agent 2 asserts the close block cannot run because the shipped file sets `sidebar_hides_panel=1`. This ignores the config's stated override. Independently, the DLL [config-load excerpt](../export/almanac-evidence/reputation-comparison-independent/effective-config.asm) loads the effective `in_panel` and hides-panel fields at `0x180048cc2–cce` and, when in-panel is active, sidebar is enabled and hides-panel is nonzero, writes `R15D` into hides-panel at `0x180048d0d`. [The loader zeroes R15D](../export/almanac-evidence/reputation-comparison-independent/config-zero-register.asm) at `0x18004823a`; no subsequent R15 write appears in this bounded path. Thus startup conditions support an effective zero, not an unconditional shipped 1. Later branches can restore or change the setting, so exact runtime state still needs validation. The H1 re-selection issue is a state-dependent hypothesis, not an established defect or consequence of that literal INI value.
- The collected body and dispatcher excerpts are useful leads, but the claim that *all* DLL content cannot run on a trade-row selection requires tracing every relevant drawing entry and gate. Do not turn an incomplete path trace into universal absence. The exact newer comparison document is not available here.
- The committed recommendation describes its proposed plugin/config-enabled session as 'read-only' and allows native skip exceptions. That label is wrong, and those exceptions do not satisfy the user's requirement that all eight remain visible and clickable. Its rollback is not demonstrated to restore all installation and process changes. No live execution is authorized.

## Second agent's revised draft summary (initial review)

At this stage the agent had corrected its uncommitted comparison, but only its pasted summary was available. The committed file was reviewed subsequently below. An independent [full selection-update excerpt](../export/almanac-evidence/reputation-comparison-independent/selection-update-full.asm) confirms another direct dispatcher call at `0x1800577b0` on the transition to the reputation-selected state. The branch at `0x18005781c` tests **EAX**, which holds the result of `0x180001c80`, not the hides-panel global itself; it may reach the dispatch through `0x1800577aa` when EAX is zero. Calls at `0x18002f7a1` and `0x18005c7aa` are also present but their full contexts have not been independently traced. This supports the agent's warning that dispatch is not unique to row selection, but not the blanket conclusion that the predicted H1 failure will occur.

The reselection branch `0x18005769c–6c4` tests effective in-panel state, reputation selection, a prior-state flag, the window predicate and the trade-row predicate, without directly testing `sidebar_hides_panel`. Reachability and subsequent close behavior can still depend on broader state and timing. Whether the hypothesized re-selection occurs in any specific mode or with a standalone design is unverified.

The counter block at `0x1800577b5–7fc` compares a difference against 30, increments a counter and, at 8 or more while hides-panel is nonzero, clears that flag. A difference of at least 30 branches to the counter reset at `0x180057888`. This is evidence of a rate-related guard on this transition path, not proof it prevents re-selection or that it counts eight *physical presses within a single 30-frame window*. The identity/units of the time source and overall behavior require more tracing.

## Review of committed comparison `6bef6fc`

The [revised comparison](almanac-alternate-content-close-comparison.md) is preserved byte-for-byte from `6bef6fce93ff4cc957dbd1620abd230da86b91f5` (Git blob `205fd841d198e59d9a11ec1f1f7ca20440932120`). Its statements that it is uncommitted are historical and no longer current; the preserved original is not edited. It correctly distinguishes the effective setting, qualifies the alternate-loop behavior, keeps content unresolved, and labels V1 a live test with all-nine acceptance criteria. It remains a useful **candidate analysis**, not a proof of operational behavior. Important qualifications:

1. **The selection-update function has a direct caller.** The draft's RT-3 and earlier mechanism report imply none was found for `0x1800575c9`, but that is an interior instruction, not the function entry. The bounded [entry](../export/almanac-evidence/reputation-comparison-independent/selection-entry.asm), [later branches](../export/almanac-evidence/reputation-comparison-independent/selection-body-branch.asm) and [caller](../export/almanac-evidence/reputation-comparison-independent/selection-caller.asm) show entry `0x180057230`, gates at `0x18005724d–261`, the transition update later in the same function, and a direct call at `0x1800687fc` within the agent-identified terrain-hook path. This is static reachability, not proof of per-frame invocation, ordering after an input event, or runtime execution.
2. **Game-side selected-record consumers are present in existing exports.** Host `0x140317f20` and `0x14031eacb`, and alternate handler `0x140361f70`, read `g_ui+0xc650 = exe+0x9e1560`. Treat the draft's blanket 'consumer not identified' as incorrect; how a particular write affects visible navigation and timing remains unproved. The exports are not authenticated against the installed binary.
3. The event table's case-0 result is **conditional on the dispatcher actually receiving 0** and its additional state, not guaranteed for every row click with flags clear. The document itself notes the argument can be a previously stored case, and its dispatcher has conditional post-processing. Statements that H1 'applies' after a click, or is a demonstrated property of a new independent Almanac implementation, should be read as a hypothesis only. H1 concerns Reputation's own state mechanism; we are not committed to using that mechanism or its DLL.
4. Screenshot inference and a read of the handler selector do not demonstrate which handler executed. Nine-tile fit, clipping, native input, repeated clicks, mode coverage, content replacement and close/return still require appropriate validation. Native skip conditions apply. The draft's assertion that native content suppression is always necessary for the separate-button option is a design assumption: a safe separate global section might navigate rather than replace the trade body. Both choices need contracts and tests.
5. The INI comments explicitly say `in_panel` forces the hide setting off, so the assertion that the comment treats it as a plain setting is inaccurate. Its stated 'frame-gap' counter units are not independently proven; the local code only establishes the difference and comparison. The counter affects the hide flag, not demonstrated prevention of re-selection.
6. V1 remains **unapproved and incomplete as an operational procedure**: it needs explicit installation/config inventory, verified executable and baseline hashes, collision/compatibility checks, a backup and exact restoration procedure, stop conditions and cleanup verification. A live test of the existing Reputation mod is not itself an Almanac proof, and user approval of research or sharing does not authorize it.
