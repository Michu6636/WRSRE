# Frontline 0.3: initial Almanac-relevant triage

**Scope:** Static inspection of the files shared in upstream commit `8f8bfd6ce344831371faafc19d0e634c07d3c7f8` and binaries added in `411cffe2b15a93b877756ec87581524ed5e55287`, not execution. This is not an Almanac implementation or a review of the entire mod.

## Files available

The upstream `Defender mod/` tree at the reviewed commit contains `install.bat`, `uninstall.bat`, PowerShell tools, configuration, language data, and images. It does **not** contain `dinput8.dll`; this repository's `.gitignore` excluded `*.dll` at that time. The user subsequently authorized removing that global exclusion. Existing ignored build directories remain excluded. [`BUILD.txt`](https://github.com/Michu6636/WRSRE/blob/8f8bfd6ce344831371faafc19d0e634c07d3c7f8/Defender%20mod/BUILD.txt) identifies the package as Frontline 0.3 public and reports DLL SHA-256 `a8c9265d41f85e4db854b14ec71b91919756640c691991717a6afb9ba0383620`. This identifier was independently verified against the later-supplied DLL, as described below.

An upstream [`dinput8_peinfo.txt`](https://github.com/Michu6636/WRSRE/blob/8f8bfd6ce344831371faafc19d0e634c07d3c7f8/export/almanac-evidence/frontline-0.3/dinput8_peinfo.txt) records an x64 PE summary and strings attributed to `dinput8.dll`. It contains several successive parser outputs, including visibly malformed earlier headers and questionable export results, so do not treat every reported header, export, address, or offset as verified. We do not have its extraction script; see the independent binary check below for corrections.

## Installer behavior from script text

- [`install.bat`](https://github.com/Michu6636/WRSRE/blob/8f8bfd6ce344831371faafc19d0e634c07d3c7f8/Defender%20mod/install.bat) launches `tools/install.ps1` using PowerShell with an execution-policy bypass. We did not run it.
- [`install.ps1`](https://github.com/Michu6636/WRSRE/blob/8f8bfd6ce344831371faafc19d0e634c07d3c7f8/Defender%20mod/tools/install.ps1) checks for a running game, performs preflight, prepares migration, conditionally backs up a pre-existing `dinput8.dll` as `dinput8.dll.before_srwar`, then copies the mod's DLL **over** the game's `dinput8.dll`. It copies data, runs vehicle/building generation scripts, and invokes migration. The backup does not establish compatibility with WRSRE's loader.
- The same script's uninstall branch removes the game's `dinput8.dll` and calls vehicle cleanup; it does not show automatic restoration of the `.before_srwar` backup. Do not run either installer or uninstaller during this investigation.
- [`defence.ps1`](https://github.com/Michu6636/WRSRE/blob/8f8bfd6ce344831371faafc19d0e634c07d3c7f8/Defender%20mod/tools/defence.ps1) generates a local Workshop building package using existing game or subscribed Workshop assets. [`fl.ps1`](https://github.com/Michu6636/WRSRE/blob/8f8bfd6ce344831371faafc19d0e634c07d3c7f8/Defender%20mod/tools/fl.ps1) generates vehicle/aircraft folders and includes cleanup operations.
- [`migration.ps1`](https://github.com/Michu6636/WRSRE/blob/8f8bfd6ce344831371faafc19d0e634c07d3c7f8/Defender%20mod/tools/migration.ps1) can back up and rewrite affected save-related files; the installer calls it. The `-CheckOnly` path should not be treated as a zero-write inspection mode: [`preflight.ps1`](https://github.com/Michu6636/WRSRE/blob/8f8bfd6ce344831371faafc19d0e634c07d3c7f8/Defender%20mod/tools/preflight.ps1) creates and deletes write-probe files, and the installer starts a transcript before checking that flag.
- [`migration_0_3.json`](https://github.com/Michu6636/WRSRE/blob/8f8bfd6ce344831371faafc19d0e634c07d3c7f8/Defender%20mod/data/migration_0_3.json) lists supported executable SHA-256 `296644a9f207d609031fc2ae73fed2dcb34619a1d55a35d1c7b51965ce6841b8`, matching the **previously reported** Almanac investigation target. This does not establish runtime compatibility or that the DLL used to generate the PE report is the same build.

## Almanac-relevant leads, not conclusions

The supplied PE text attributes strings such as `buildmenu: tab %s added as #%zu with %d buildings`, `buildmenu: menu builder call redirected`, and `buildmenu: industry frame rect ... pitch ...` to the binary. Those strings suggest a potentially relevant **build-category/menu** implementation to investigate. They do not identify an instruction, prove the path executed, explain how it works, or establish that it uses the Almanac's Economy & Trade row or suppresses its content. Other strings mention ImGui and Direct3D; their presence alone does not establish how the army/economy switch works.

## Subsequent Windows-agent findings (reported, not independently verified)

The user relayed that the Windows agent hashed the 4,635,648-byte DLL as `a8c9265d41f85e4db854b14ec71b91919756640c691991717a6afb9ba0383620`, matching `BUILD.txt`, and successfully analyzed it in a separate Ghidra scratch project. Its decompile post-script failed to resolve Ghidra API classes; no instruction-level decompilation was produced. The agent reported PE exports and DX11/COM imports, and identified strings suggesting a proxy, a build-menu redirect and ImGui. Imports and strings alone do **not** prove a working proxy, swap-chain hook, actual control flow or which UI uses ImGui. Its report and PE output are at `C:\WRSRE\export\almanac-evidence\frontline-0.3\` on the user's Windows machine; the report has not been made available in this checkout. F8 behavior was reported from mod documentation, not verified here.

The user has permitted DLL files in Git; that permission is not itself proof of a third-party redistribution license. The Windows agent initially reported that it had not copied or committed the DLL; it was subsequently committed upstream.

## Independent binary check

The two DLLs subsequently appeared in upstream commit `411cffe2b15a93b877756ec87581524ed5e55287`. We inspected them as data, without executing them. `Defender mod/dinput8.dll` hashes to `a8c9265d41f85e4db854b14ec71b91919756640c691991717a6afb9ba0383620`; `tools/C3DDLL64.dll` hashes to `65fcb6845c3cb7c25a22121f25904a855ea88657e31a3b50a15adac26e231516`. The Windows agent's [original report and PE text](../export/almanac-evidence/frontline-0.3/) are preserved unchanged; [our bounded disassembly and PE summary](../export/almanac-evidence/frontline-independent/) provide independent raw evidence.

- The original report's Frontline export mapping is incorrect: the PE export table maps `DirectInput8Create` to RVA `0x5592`, `DllCanUnloadNow` to `0x137c8`, and `DllGetClassObject` to `0x7fb8`, ordinals 1–3 respectively. A zero RVA is not evidence of a proxy forwarder. The report's quoted `buildmenu` string numbers are **file offsets**, not RVAs: for example offset `0x392ba0` maps to RVA `0x3943a0`. Do not use the original report's export or string-address claims without correction.
- At Frontline preferred VA `0x18007a3c0`, the code asks `GetModuleHandleA(NULL)` for the main module, checks five bytes at module RVA `0x2f0eca` against `e8 61 0f d6 ff`, and takes a failure path if they differ. On the matching path it calls `VirtualAlloc` near that module, writes a 12-byte absolute-jump stub targeting DLL VA `0x18007a050`, changes protection and replaces the **four-byte displacement** of that existing five-byte `call`, then restores protection and flushes the instruction cache. The original call would target module RVA `0x51e30`; the stub's target calls that same module-relative address and then tail-jumps to another Frontline routine. This substantiates a specific, signature-checked build-menu redirect in the binary; it does not prove it ran or that this exact game executable was present. It is not a general safe-hook recipe.
- The new `C3DDLL64.dll` export table independently confirms `C3D_PANEL2D::Collision` at RVA `0xbc690` and `C3D_PANEL2D::Draw` at RVA `0xbaf40` for this file. This corrects the prior lack of name-to-RVA verification, but does not independently identify the user's runtime DLL or establish clipping, field meanings, or behavior.

## Next bounded step

Return to the Almanac-specific path rather than porting Frontline's build-menu hook. The remaining design gates are the ninth same-row button's dynamic layout and input, safe vanilla-content replacement, and close/return behavior. Review them against the existing native trade-handler evidence; when the game is available, use the already-approved non-pausing, read-only snapshot to resolve runtime geometry and selection state. Then decide whether a separate global section is safe, with an Economy & Trade page as fallback. The first implementation must include adjustable taxes, with configured-policy getters where needed. No game implementation or hook is authorized by this investigation alone.
