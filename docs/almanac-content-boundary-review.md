# Sidebar content-boundary proposal: independent review

The agent's [report](../export/almanac-evidence/sidebar-content-replace-20261110/report.md) from `5be6023` is preserved unchanged. The independent [caller and later-dispatch excerpts](../export/almanac-evidence/content-replacement-independent/callers-and-later-dispatch.asm) come from the existing tracked host and handler exports. This is static analysis; it neither proves execution nor approves implementation.

## Decision

`0x140374606` is a **candidate for further analysis**, not a demonstrated clean content-replacement boundary. The report itself acknowledges remaining content and input after the call, unknown cleanup, and another trade handler. That conflicts with its recommendation that native input is preserved with no contention and that only the complete page body is replaced. We cannot recommend hooking or skipping this call as a finished solution.

## Evidence and corrections

1. In `FUN_140373EA0`, `0x1403745f1–f8` uses an **unsigned** comparison. On the path that reaches it, indices 0 and 1 call `FUN_14035F3E0` at `0x140374606`; all unsigned values above 1, including `0xffffffff`, bypass that call. A mod-owned open flag does not change the native index: if the user opens the Almanac while a native index above 1 is selected, this call-site cannot by itself intercept the page. This matters for the requirement that the new button work alongside all eight icons.
2. Other native selection-based paths continue later. For example, at `0x140374a78–acc` the handler reads the selected index and, for indices 3/4, conditionally calls `0x1404b3230`; at `0x140374ad6–b35` and `0x140374b60–bbf`, other indices lead to different helper calls. Their full visual and input behavior has not been independently established; their existence alone refutes the notion that replacing `0x14035f3e0` handles every selected page. It also makes 'otherwise nothing' unsupported.
3. The caller immediately reloads the output-related local at `[RSP+0x70]` and tests `AL` (`0x14037460b–619`). Prior [helper decompilation](../export/almanac-evidence/fun-14035f3e0-20261108/) shows a write through its third parameter as well as drawing and native state/input side effects, on its decompiled normal path. Skipping or replacing the call requires an evidence-based contract for output local, return, side effects and downstream cleanup. Simply NOPing a call and retaining `TEST AL,AL` would risk a stale result. This is not proved safe by returning an arbitrary value or copying a few state writes.
4. `FUN_140361BB0` has a second conditional call to the same helper at `0x1403628b8`, gated by `R15 == 0` and unsigned selected index <= 1; `AL` and an output local are consumed afterward. This was already present in [`ch_tab23_full.asm`](../export/ch_tab23_full.asm) and the [export review](almanac-export-review.md). The report's claim that the alternate path is wholly untraced is too broad; its full behavior and suppression/cleanup remain unresolved.
5. `0x14031ee02` stores the caller's derived value into `game+0xae58` **after** `0x140373ea0` returns. It is not an instruction inside that handler; the effect of bypassing that handler while retaining the subsequent store must be analyzed from actual outputs, not classified as a skipped store by address alone.
6. The claims that `game+0xadb0` dimensions were set at construction and that clipping occurs inside specific Draw/Collision methods are not proven by the supplied report: it did not preserve the cited helper bodies, constructor or full clipping path. Our existing [independent review](almanac-export-review.md) also warns against those claims. The `ui_panels` foreign path comment says it skips a clip push to avoid trapping ESC, not that skipping it causes ESC to be blocked. No cited evidence establishes that the building-window ESC dispatcher governs this global sidebar.

## Follow-up `bbd66ca`: alternate handler evidence was already tracked

The [follow-up report](../export/almanac-evidence/sidebar-compare-20261110/report.md) is preserved unchanged. Its claim that `0x1403628b8` was not found in its Windows scratch cache is not evidence that the call does not exist. The tracked repository file [`export/ch_tab23_full.asm`](../export/ch_tab23_full.asm), available on both the session base and remote `Almanac`, contains it at line 655. In the LF checkout its SHA-256 is `5579ae618eb7be20d3cd89c933dd1cddfcefbb6cefcc320b8df01c93c30ec79d`; Git blob ID is `ecb092b44e6fffb518be24e0bc8fe1be1a2e70f0`. A Windows checkout's SHA-256 may differ if line endings are converted. The independently selected [excerpts and relative-call arithmetic](../export/almanac-evidence/alternate-handler-compare-independent/excerpts.txt) show `E8 23 CB FF FF` at `0x1403628b8` targeting `0x14035f3e0`, gated by `R15 == 0` and unsigned `[R14+0xc65c] <= 1`, followed by `TEST AL` and reload of `[RBP-0x20]`. The instruction export remains static evidence, not a runtime trace or independent verification of the original game binary's identity.

The report misidentifies two other instructions: `0x14036252b` is a **load** of the index, not `CMP index,1`; `0x1403626d7` is a **call** to `0x140445eb0`, not `CMP index,2`. On the shown path, `0x140362532–53d` checks for 3/4 and conditionally calls `0x1404acf50`; `0x140362547–54f` checks for 5 and calls `0x1404b0e20`; selection 6 has another conditional call. Additional guards and reachability remain important. A direct index write at `0x140362193` in this alternate handler also shows why the earlier inventory restricted to three functions was not exhaustive.

The report's 'go' claims are too strong: the native row loop being before a potential content boundary does not demonstrate a safe hook, preserved shared draw/input state, coexistence with the extra button, or valid cleanup. 'No replacement needed' when `0x14035f3e0` is bypassed also does not follow—later native content paths may still run. AL's observed use and the modified output local must be accounted for, but simply replicating an asserted click-indicator value or accepting skipped writes is not proven safe.

## Next analysis and acceptance gates

A focused follow-up can use the **tracked alternate-handler export** without opening or unlocking Ghidra. Compare the two handlers' actual selection branches and early exits, and document candidate interception paths including locals, subsequent native content, and cleanup, preserving exact instructions and known unknowns. If a Ghidra process is still running or the project is locked, investigate the lock owner rather than deleting lock files or running concurrent analysis.

A separate mod-owned button and global page remain candidates, not finished implementations. Another native snapshot cannot establish a new button's clipping, same-row placement, input arbitration, tax controls or safe return. Any game modifications, hooks, deployment or integration testing require explicit separate user authorization.
