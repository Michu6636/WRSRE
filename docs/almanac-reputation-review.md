# Reputation 2.0: independent static review

**Sources:** DLL and configuration from upstream `73a0763f2b7d608b5b73e95be58ae40993064d61`, `Mods for analysis/Diplomacy/tesmioloader/the build/plugins/`; Windows agent's original [report and evidence](../export/almanac-evidence/reputation-mod/) from `b1962847b5ad50eb4b6bcda433ea442150bb60b4`, preserved unchanged. We independently inspected the files as data without running the mod, scripts or game. Our [bounded raw disassemblies, PE summary and configuration excerpts](../export/almanac-evidence/reputation-independent/) are also preserved.

The DLL is 825,344 bytes; SHA-256 `fd7d94590b98c7eb80fa14ef95f2bbdf4b5e058f68d07dfa97d0db8dcbfbcb6a`, matching the Windows report. The configuration SHA-256 is `6dcc7479ae95c0bf14111591328e0361987767ad34c8ba0273483add89ec1e43`. These hashes identify the files inspected, not the runtime installation.

## Directly relevant: the optional Economy & Trade item

The supplied configuration lines 1589–1630 describe a disabled-by-default `sidebar_item = 0`, with `sidebar_item_panel = trade` and `sidebar_item_name = reputation`. Its comments **claim it was tested successfully**, displaying an extra Economy & Trade icon and opening the mod window. That is a mod-author claim, not our runtime observation. The config identifies the trade panel's eight existing items with the target row; it says the option requires the separate sidebar entry. The report initially classified this path as uncorroborated in code; the DLL now supplies useful static support:

- The function at DLL VA `0x180057e40` searches records in the array pointed to by executable base `+0x9e1518` with stride `0x68`, compares a configured panel name, and checks the candidate's vector header at record `+0x48`. It validates that the existing vector span is a nonzero multiple of `0x50`, checks its readability, and searches entries by name. See [item-add disassembly](../export/almanac-evidence/reputation-independent/item-add-objdump.asm).
- On a later path it builds a zero-initialized `0x50`-byte stack record, then calls **executable base `+0x4492f0`** with that record and the vector header. This matches the separately preserved [game helper disassembly](../export/almanac-evidence/FUN_1404492f0_disasm.asm), which copies a `0x50`-byte entry and advances the vector end, with a conditional growth helper. This is a stronger connection to our prior trade-row investigation than Frontline's build-menu hook. The game EXE itself and runtime call are not independently verified in this review.
- The subsequent code attempts to obtain a texture, stores it into the final entry, checks that slot and, on a null slot, subtracts `0x50` from the vector end. These instructions do not by themselves establish all failure, concurrency, allocation, cleanup or ownership safety.
- The helper at `0x180058310` checks the currently selected panel name and compares a DWORD at executable base `+0x9e156c` with a stored item index; `0x18005761e–0x180057692` calls it and reacts on a change, reaching a diagnostic string about the item being chosen. See [selection](../export/almanac-evidence/reputation-independent/item-selected-objdump.asm) and [UI update](../export/almanac-evidence/reputation-independent/ui-update-objdump.asm) disassemblies. This is evidence of the plugin's recognition logic, not proof of where the game writes the index or how every input path works.

The config's statements are not a substitute for a runtime placement/click test. The known alternate game handler can omit index 8; count, layout, clipping, selection and the exact active handler remain contextual. This evidence does **not** establish safe suppression of vanilla content, navigation back, or safe reallocation of the game's vector. Do not port the third-party implementation.

## Sidebar and original report corrections

- The export table independently maps `TsmPluginApiVersion` to RVA `0x68be0`, `TsmPluginInit` to `0x68bf0`, and `TsmPluginStart` to `0x68f30`, ordinals 1–3. The original PE text and narrative shift the mappings; the original function list and supplied Start disassembly correctly identify Start at `0x180068f30`.
- The Start disassembly calls a function with strings `sites` and `build_stamp`, saves its return to `RDI`, checks the executable's `MZ`/`PE` signatures and compares the PE header timestamp with `EDI`. The config lists `build_stamp = 0x6A3EB6AD`. The original report incorrectly identifies `0x1801a15c0` as the source of that comparison: it is loaded **after** it. On a matching timestamp this path sets a plugin flag, and the item-add path checks that flag before its normal work. Timestamp equality is not a binary hash or a safety guarantee; not every hook is proven gated by it.
- The constants `0x31e478` and `0x31e509` at `0x18006944e–0x180069460` are supplied to a diagnostic call. The preceding indirect API calls use strings naming `C3D_PANEL2D::SetDimensions` and `SetPosition`, consistent with IAT-patching through the loader, not proof that the constants themselves are inline-hook targets. The `0x31f03c` occurrence is also a diagnostic argument. Callback internals and actual runtime bindings still need tracing.
- At `0x180069317–0x18006932f`, the check against `0x187a` passes a **diagnostic format string**, not the literal `Diplomacy`, to the helper. It does not prove a GetString result was swapped at that instruction. The configuration describes a title override; follow its actual hook before asserting the mechanism.
- Config lines 1502–1527 say `sidebar = 1`, `sidebar_hides_panel = 1`, and `in_panel = 1`, **but also say in-panel mode forces `sidebar_hides_panel` off**. Therefore the Windows summary's unconditional push-to-open/push-to-close description does not follow from the shipped values. The same configuration claims the sidebar is cloned from a native entry, but its three undecoded fields, runtime behavior, content drawing and cleanup remain to be independently traced.
- These configuration comments include historical contradictions: for example they describe the build tab and sidebar as off by default while their values are `1`. Report exact supplied values rather than inferring the state of a user's installed copy.

## Independent follow-up: panel geometry writes

A focused static recheck of the same hash-matched DLL found additional evidence not previously captured; [host-binding and bounded panel excerpts](../export/almanac-evidence/reputation-panel-geometry-independent/) are preserved separately. At `0x180068c22–26`, the DLL saves the host table's `+0x10` field to `0x1800c4d80`; the repository's [`TsmHost`](../src/tesmio_api.h) defines that field as the executable base. At `0x180028128` and `0x180028149`, conditional stores write floats to that base plus `0x9dfd64` and `0x9dfd68` respectively. Since `0x9d4f10 + 0xae54 = 0x9dfd64` and `0x9d4f10 + 0xae58 = 0x9dfd68`, these support game-object-relative geometry writes. A second bounded path has corresponding stores at `0x180058b23` and `0x180058b2b`, again guarded by surrounding conditions.

This strengthens the evidence that the DLL can write those fields; it does not prove when those paths run, that they are specifically executed from SetDimensions/SetPosition detours, that their values are universally right/bottom edges, or that an Almanac can safely reuse them. The configuration describes panel positioning and moving its right edge, not simply increasing width; its comments are developer claims, distinct from observed behavior. The separate-item insertion path described above constructs a **zero-initialized record**, names it, then uses the game's insertion helper; that is not evidence that it copies and appends a donor item on every frame. The configuration describes a **different**, main left-sidebar entry as cloned. Both modes deserve investigation as related but distinct paths.

## Follow-up review: supposed click and close functions are unrelated

We reviewed the agent's subsequent report and raw excerpts from upstream `f0727a4161b873ba0f3e304d9f492e32a60f8284`; [the exact source files](../export/almanac-evidence/reputation-followup-agent-f0727a4/) are preserved separately without replacing the earlier report. The same DLL's hash still matches above. [Independent objdump excerpts, string bytes and import table](../export/almanac-evidence/reputation-followup-independent/) show material misidentifications:

- The four wrappers at `0x180068a20`, `0x180068a80`, `0x180068ae0`, and `0x180068b40` are **not established to be item-vtable callbacks**. At `0x180069834–0x180069949`, the plugin passes strings `api-ms-win-crt-stdio-l1-1-0.dll`, `fopen` and `fopen_s`, these wrappers, and storage for original function pointers to the loader API. The labels also say `engine fopen` and `engine fopen_s`. This is file-open interception evidence, not button creation, rendering or activation. The DWORD at `0x1800c3090` guards this path and the helper below, but the agent's assertion that it is the `sidebar_item` setting is unsupported.
- `0x1800303e0` examines file paths and modes including `r`, `w`, and `a`; its resolved strings include `save`, `buildings_game.bin`, `runningScripts.bin`, `city_names.txt`, and a sidecar warning about save data. It is not shown to be a UI click/selection/panel-open fallback. The supplied excerpt continues past its `RET` at `0x1800306f6` into a different function at `0x180030700`.
- `0x180068ba0` zeroes a plugin pointer and calls **through an import slot**, not a virtual method on a panel. The disk import table maps slot `0x18008d2e8` to USER32 `UnhookWindowsHookEx`; no runtime binding is proved. This is not evidence of a close/return handler or native panel restoration. The old pointer is loaded into `RCX`, not exchanged into `RAX` as the report claims.
- The report repeats earlier incorrect claims about the title swap, panel hook constants and unconditional push-button behavior. See the corrections above. Its claim that the `0x140358a20` handler is effectively dead is not established by its excerpts; do not discard either game-handler path.

These corrections do **not** negate the independently decoded `0x180057e40` item-vector insertion or `0x180058310` selection comparison described above. The caller at `0x180057628–0x180057678` tracks changes in the comparison result and, under additional conditions, calls `0x18002f1e0` with a stored integer. [That helper](../export/almanac-evidence/reputation-followup-independent/item-response-helper.asm) dispatches on an index and changes several plugin globals. The exact meaning of each global, the panel-open sequence and return to native content are not yet established. The complete button-to-panel and close/return implementation remains unverified.

## Corrected agent trace: independent follow-up

The [later agent report and raw exports](../export/almanac-evidence/reputation-corrected-agent-f591636/) are preserved from upstream `f591636e4678ada9e93f93bd89e9fa4953dc0090` without changing either previous report. [Independent state-helper decode, jump table and direct-reference scan](../export/almanac-evidence/reputation-corrected-review/) use the same hash-verified DLL. The report correctly returns to `0x180058310` and its caller, and its selection-change branch is broadly consistent with the instructions. However:

- The seven addresses in `0x18002f1e0` are **DLL-local globals**, not established game globals. RIP-relative instructions resolve inside Reputation's own `.data` section. Many direct references are present in Reputation's own code, as the reference scan shows. It is unsupported to say the game's native code reads them, or that they directly represent vanilla game state. Their meanings and consumers need tracing in the plugin.
- The integer loaded from DLL global `0x180411bcc` is **not established to be the trade-item index**. Immediately before selection handling, `0x180057600–0x180057617` checks eight numbered plugin-state cases using `0x18002f120` and records the first one that returns true. The actual selected trade-item index is compared separately at executable base `+0x9e156c` against DLL `0x1800c3c5c`. The former may represent a remembered plugin window/tab; do not conflate them without more evidence.
- The jump-table destinations in the report match the decoded table, but several case descriptions reverse conditions or omit toggles. In case 0, `0x1800c3158` becomes **2 when previously zero, otherwise 0**. Case 1 toggles `0x180286080` to 1 if zero, otherwise 0. Cases 2, 3 and 6 skip their toggle when their respective guard is zero; when enabled they toggle the corresponding state. Case 7 toggles rather than always clearing. The common tail conditionally clears other states; it is not proof of a specific open/close operation.
- `[host+0x60]` matches the current `TsmHost::readablePtr` API signature (`src/tesmio_api.h`), receiving an address and length; the constants 8, 0x17 and 4 in the excerpt are lengths, not API IDs. Exact ABI compatibility with the mod's build needs verification.
- The report's ranges include following functions or table bytes: `0x180058310` returns by `0x1800583d7`, with another function at `0x1800583e0`; `0x180057230` ends by `0x180057924`, with another at `0x180057930`; `0x18002f1e0` returns at `0x18002f3f4` and its jump-table data starts at `0x18002f3f8`. Do not interpret later bytes as part of those functions. Its PE export addresses also repeat the earlier error corrected above.
- No suppression or restore was shown in the **bounded** excerpts. That does not prove the mod never suppresses native content or that closing fully restores it. Nor do these excerpts establish which game handler runs. The author's config remains a useful runtime claim, not our own observation.

## Contracts-board consumer: independent check

The user relayed a later local-agent report about case 1 of `0x18002f1e0` and its consumer `0x18001e0a0`. Its raw files were not yet present in the upstream tree when checked; [independent objdump and string excerpts](../export/almanac-evidence/reputation-consumer-independent/) were generated from the same hash-verified DLL.

- Case 1 toggles plugin-local `0x180286080` and clears `0x180286084`. At `0x18001e0c3`, the consumer tests the first flag and jumps to its epilogue when it is zero. Its normal path refers to contract-board strings including `CONTRACTS`, `Nothing running and nothing offered` and `The board is redrawn every few weeks`, and calls `0x180022c50` with text and coordinates. That helper converts the input into a wide string and conditionally calls through a stored function pointer. This supports the agent's interpretation of mod-owned contracts UI, but a static excerpt does not prove actual runtime drawing or resolved callback identity.
- A direct call at `0x1800610bb` targets the consumer in the wider dispatcher at `0x180060e20`. One matching direct call was found in the objdump text; this is not proof that indirect calls or runtime callbacks do not exist. The consumer contains **17 static call instructions** to `0x180022c50`, not only three; conditional branches determine which run. The log string at `0x18009be08` identifies the neighboring clear-to-zero path as `contract window faulted - window off`; it should not be labeled normal user-close behavior without further control-flow proof.
- The local-agent summary again asks which *game* code reads the DLL globals. That premise is not established: prior scans show the DLL's own code reads them. These bounded excerpts cannot prove that the plugin never suppresses vanilla content or restores selection, only that those operations were not demonstrated here.

## Next investigation

The contract-window consumer distinguishes plugin-owned UI state from native trade selection. The user has now explicitly asked whether Reputation's panel approach can be reused, and the panel-geometry follow-up above adds concrete leads. Trace the **actual panel-placement callbacks, selection lifecycle, and rendering/return path** with preserved instructions and settings; compare the separate global sidebar entry and optional trade-row item, rather than assume that they are the same mechanism. In parallel compare the game's known row ordering and alternate loop, and evaluate both native insertion and a dynamically positioned independent button against the user's requirement for all eight native icons and the new button in one row. A selector snapshot alone does not prove execution. Directly adjustable taxes remain in the first release; no game implementation, execution, hook or redistribution is authorized by this review.
