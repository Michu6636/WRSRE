# Reputation 2.0: independent static review

**Sources:** DLL and configuration from upstream `73a0763f2b7d608b5b73e95be58ae40993064d61`, `Mods for analysis/Diplomacy/tesmioloader/the build/plugins/`; Windows agent's original [report and evidence](../export/almanac-evidence/reputation-mod/) from `b1962847b5ad50eb4b6bcda433ea442150bb60b4`, preserved unchanged. We independently inspected the files as data without running the mod, scripts or game. Our [bounded raw disassemblies, PE summary and configuration excerpts](../export/almanac-evidence/reputation-independent/) are also preserved.

The DLL is 825,344 bytes; SHA-256 `fd7d94590b98c7eb80fa14ef95f2bbdf4b5e058f68d07dfa97d0db8dcbfbcb6a`, matching the Windows report. The configuration SHA-256 is `6dcc7479ae95c0bf14111591328e0361987767ad34c8ba0273483add89ec1e43`. These hashes identify the files inspected, not the runtime installation.

## Directly relevant: the optional Economy & Trade item

The supplied configuration lines 1589–1630 describe a disabled-by-default `sidebar_item = 0`, with `sidebar_item_panel = trade` and `sidebar_item_name = reputation`. Its comments **claim it was tested successfully**, displaying an extra Economy & Trade icon and opening the mod window. That is a mod-author claim, not our runtime observation. The config identifies the trade panel's eight existing items with the target row; it says the option requires the separate sidebar entry. The report initially classified this path as uncorroborated in code; the DLL now supplies useful static support:

- The function at DLL VA `0x180057e40` searches records in the array pointed to by executable base `+0x9e1518` with stride `0x68`, compares a configured panel name, and checks the candidate's vector header at record `+0x48`. It validates that the existing vector span is a nonzero multiple of `0x50`, checks its readability, and searches entries by name. See [item-add disassembly](../export/almanac-evidence/reputation-independent/item-add-objdump.asm).
- On a later path it builds a zero-initialized `0x50`-byte stack record, then calls **executable base `+0x4492f0`** with that record and the vector header. This matches the separately preserved [game helper disassembly](../export/almanac-evidence/FUN_1404492f0_disasm.asm), which copies a `0x50`-byte entry and advances the vector end, with a conditional growth helper. This is a stronger connection to our prior trade-row investigation than Frontline's build-menu hook. The game EXE itself and runtime call are not independently verified in this review.
- The subsequent code attempts to obtain a texture, stores it into the final entry, checks that slot and, on a null slot, subtracts `0x50` from the vector end. These instructions do not by themselves establish all failure, concurrency, allocation, cleanup or ownership safety.
- The helper at `0x180058310` checks the currently selected panel name and compares a DWORD at executable base `+0x9e156c` with a stored item index; `0x18005761e–0x180057692` calls it and reacts on a change, reaching a diagnostic string about the item being chosen. See [selection](../export/almanac-evidence/reputation-independent/item-selected-objdump.asm) and [UI update](../export/almanac-evidence/reputation-independent/ui-update-objdump.asm) disassemblies. This is evidence of the plugin's recognition logic, not proof of where the game writes the index or how every input path works.

The config's statements are not a substitute for a runtime placement/click test. The known alternate game handler can omit index 8; count, layout, clipping, selection and the exact active handler remain contextual. This evidence does **not** establish safe suppression of vanilla content, navigation back, or safe reallocation of the game's vector. Do not port the third-party implementation.

## Sidebar and original report corrections

- The export table independently maps `TsmPluginApiVersion` to RVA `0x68be0`, `TsmPluginInit` to `0x68bf0`, and `TsmPluginStart` to `0x68f30`, ordinals 1–3. The original PE text and narrative shift the mappings; the original function list and supplied Start disassembly correctly identify Start at `0x180068f30`.
- The Start disassembly calls a function with strings `sites` and `build_stamp`, saves its return to `RDI`, checks the executable's `MZ`/`PE` signatures and compares the PE header timestamp with `EDI`. The config lists `build_stamp = 0x6A3EB6AD`. The original report incorrectly identifies `0x1801a15c0` as the source of that comparison: it is loaded **after** it. On a matching timestamp this path sets a plugin flag, and the item-add path checks that flag before its normal work. Timestamp equality is not a binary hash or a safety guarantee; not every hook is proven gated by it.
- The constants `0x31e478` and `0x31e509` at `0x18006944e–0x180069460` are supplied to a diagnostic call. The preceding indirect API calls use strings naming `C3D_PANEL2D::SetDimensions` and `SetPosition`, consistent with IAT-patching through the loader, not proof that the constants themselves are inline-hook targets. The `0x31f03c` occurrence is also a diagnostic argument. Callback internals and actual runtime bindings still need tracing.
- At `0x180069317–0x18006932f`, the check against `0x187a` passes a **diagnostic format string**, not the literal `Diplomacy`, to the helper. It does not prove a GetString result was swapped at that instruction. The configuration describes a title override; follow its actual hook before asserting the mechanism.
- Config lines 1502–1527 say `sidebar = 1`, `sidebar_hides_panel = 1`, and `in_panel = 1`, **but also say in-panel mode forces `sidebar_hides_panel` off**. Therefore the Windows summary's unconditional push-to-open/push-to-close description does not follow from the shipped values. The same configuration claims the sidebar is cloned from a native entry, but its three undecoded fields, runtime behavior, content drawing and cleanup remain to be independently traced.
- These configuration comments include historical contradictions: for example they describe the build tab and sidebar as off by default while their values are `1`. Report exact supplied values rather than inferring the state of a user's installed copy.
