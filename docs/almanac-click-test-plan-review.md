# Click observer test plan: independent review

The agent's [original plan](../export/almanac-evidence/native-click-hookpoints-20261110/test-plan.md) from `d5bb373` is preserved unchanged. The plan is **not authorized or ready to execute**. It usefully separates a click observer from the unsolved Almanac button, content and return problems, but its pass criteria and safety instructions need revision.

## Corrections before any authorization

- **A running inline hook modifies executable code in the game process.** Loading a DLL and changing executable bytes are process modifications even if only an observer flag/counter is changed afterward. The two original stores must still execute and write game state. P8/F8 and the instruction 'does not write to any game memory' conflict with the plan itself. The correct goal is a precisely documented temporary code patch and expected original game writes, with no unintended mod-origin writes to game state—not a claim that no game memory changes. Building writes local files but need not touch the running game.
- A mid-function detour must preserve **all live state**, including volatile general-purpose/vector registers, flags, stack and ABI state as required by the actual continuation. Merely preserving ABI-nonvolatile registers is not enough. The existing loader copies stolen bytes and does not itself establish that a mid-function callback, stack layout, unwind handling, relocated execution or hook lifetime is safe.
- Its displayed byte strings omit immediate bytes and candidate B's REX prefix. Compare the complete actual 16-byte or 18-byte span against the current process after verifying the full executable hash and reacquiring the module base; abort without modifications on mismatch. Preferred-image addresses in the report are not live process addresses. Independent counts are [here](../export/almanac-evidence/native-click-boundary-independent/byte-counts.txt).
- The test matrix assumes visual icon position equals vector index. In the analyzed `373EA0` normal loop the third visual position is the last mapped entry, not index 2; skips change positions. The other handler can omit the last element. Label test icons by the actual observed entry and index, not by a guessed left-to-right number, and document active handler/mode without inferring execution from selector alone.
- `game+0x10be8` is reset before the row on both handler paths, independently of clicks; its value is neither a unique click event nor guaranteed to remain unchanged during hover. Non-atomic `PROCESS_VM_READ` snapshots taken after a click do not prove which instruction ran or that no other state changed. If counters/flags record events, use a bounded, race-safe per-event sequence and a separately controlled way to identify which hook fired; a sticky flag or a frame-only sample is inadequate for duplicate and rapid clicks. A previous observer index is not necessarily the index selected before the first observed event.
- Test every visible native icon and repeated current selection, hover, off-row interaction, switching sections and normal close, along with user input and graphics regressions. Separate eligible observed paths from unavailable/untested modes: a failure of one candidate or environment does not automatically reject the other or every other approach. The current single-candidate plan cannot prove both handlers or an unbuilt ninth button.
- A safe environment and rollback require inventorying/backing up existing loader and plugin files and configuration, preserving the original installation, and a disposable save/backup before execution. Never overwrite an existing `dinput8.dll` or remove another plugin blindly. Stop on crash, unexpected writes or input regression; restore exactly the recorded baseline and verify. This is a proposal, not authorization for an installer, file change, save change or game execution.

## Scope

Even a successful authorized observer experiment would show only measured click-path behavior for that build and environment. It would **not** prove the Almanac button fits, that content safely replaces vanilla content, that navigation works, or that tax policy controls are correct. Compare the observer approach against Reputation's native-insertion approach before choosing a proof of concept; the UI integration decision remains open.
